# USB 磁盘切换失联记录

## 结论

2026-09-19 切换磁盘模式后，电脑同时失去串口与磁盘入口；用户报告疑似死机，重启后恢复。**恢复连接已证实；死锁位置与切换故障修复尚未证实。** 串口消失本身不能用作 USB 磁盘开启成功的回执。

## 已确认的边界

- 切换请求只收到排队回执。随后 `/dev/cu.*`、IOUSB 与外置磁盘清单均没有可用设备。
- 此次没有复制 SD 更新包，也没有通过磁盘更新固件。
- 用户重启后，原设备身份 `1020ba6e0be0`、perf2、运行地址 `0x80000` 恢复。
- 后续通过 ROM 单独更新应用区，保留原5MiB应用槽备份；perf3、perf4均单独读取写入范围并比对 SHA256。
- 不采用格式化 SD、修改 eFuse 或绕过保护作为恢复手段。

## 源码线索（不能直接称为本次根因）

`main/boards/common/usb_virtual_disk.cc` 的启动顺序：建立本机 MSC 存储 → 切 PHY → 安装 TinyUSB → 将 SD 切给主机。

1. `MountToUsb()` 在主机可能已开始枚举之后执行。应验证是否有早期主机 I/O 与 SD 卸载互相等待；候选改法是在开放 USB 枚举前完成 SD 交接，同时处理所有失败回退。
2. `UsbEventCb` 在 `s_usb_switching` 为真或 gadget 未标记 active 时直接返回，可能遗漏初始 ATTACHED 事件，进而影响后续弹出识别。需要保留连接边沿并在切换结束后协调状态。
3. 当前 TinyUSB 的 `msc_storage_unmount` 等待 `storage->mux_lock` 使用无限等待；缺少阶段证据，不能判断本次是否卡在这里。
4. `paper_maintenance::Tick` 在 gadget active/busy 时一直等待，因此不能独立证明切换取得进展。不能简单超时强行夺回正在被主机写入的 SD。

## 再次实机复现前的要求

- 记录切换阶段与上次重启原因，确保失去串口后仍能在重启后读取阶段证据。
- 保留已验证的 ROM 下载入口和应用镜像；不要在唯一调试通道消失后盲目连续重试。
- 电脑验收必须包含：实际磁盘枚举、只读文件访问、安全弹出、串口恢复、设备端 SD 文件校验。
- 自动恢复只可在确认没有主机写入/已安全卸载的条件下操作；否则保留明确故障信息，要求安全重启或物理介入。

本记录不宣称磁盘切换已修好。当前设备保留串口调试模式，先完成不依赖 MSC 的自动测试。

## perf6 后续实机验证

上述历史阻碍已取得一次成功闭环：SD先交接再枚举、底层返回值传播、连接边沿补偿和回挂错误处理后，Mac识别到15.9GB USB磁盘；只读测试书哈希与调试上传回执一致；安全弹出成功，串口返回，设备端再读同一书哈希一致。没有格式化、复制或删除用户文件。

仍有独立限制：Mac重新打开串口时日志出现 `USB_UART_CHIP_RESET`，设备重启。RTC保留的USB阶段为8（切换完成）。因此“磁盘→安全弹出→设备读SD/调试恢复”已一次PASS；“无重启连续会话”仍NOT_PROVEN，不能把这次结果扩展成长期或快速拔插稳定性保证。
